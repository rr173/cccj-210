# histoware — 延迟直方图检查点入仓、班次汇总与班次回归归因工具

配送平台只保留各采集器定时上报的**累积延迟直方图检查点**，不收集原始请求。
本工具做四件事：

1. `load`：把 JSONL 累积检查点**按批**装入本地 SQLite 仓库，整批成功后分配递增、可查询的入仓版本；
2. `summary`：给定入仓版本 + 值班表 + 若干命名班次，产出一份可直接消费的 SQLite 结果库，
   区分**精确计数**、**只能给出上下界的计数**、以及**因覆盖不全不能给出总体计数**三种情况，并保留全部来源证据；
3. `attribute`：读取**两份已经生成的结果库**和一份显式配对清单，产出可查询、可追溯的 SQLite
   对比库，回答“本周某 SLO 切点的延迟恶化由哪些采集器贡献”。它**只读取结果库**，
   绝不重新读取原始检查点，也绝不重算任一侧的班次汇总；
4. `mirror`：把端点的**当前选中行**按订阅打包成可逐条校验的包文件，中心导出、现场离线接收进
   独立的 SQLite 镜像库并直接查询（见[检查点镜像（mirror）](#检查点镜像mirror)）。

此外 `retire` 子命令提供**可预演、可批准、原子执行的版本退役**：把仓库收窄到最近一次核准的水位，
只为正在复盘的老版本保留例外，并把不再可能被任何可回放版本选中的检查点载荷真正腾退（见
[版本退役（retire）](#版本退役retire)）。它不需要用另一个工具重做班次汇总，也不改写已生成的结果库。

只依赖 Python 标准库（Python ≥ 3.8），无需安装第三方包。

## 输入格式

### 检查点 JSONL（每行一个对象）

```json
{"region":"cn-1","collector":"a","generation":"g1","ts":1700000000,"revision":0,"cuts_ms":[10,20],"counts":[2,5],"total":7}
```

* 以 `(region, collector, generation, ts)` 标识一个检查点，`revision` 为非负整数修订号；
* `ts` 为 UTC 整秒；`cuts_ms` 为严格递增的正整数毫秒切点；`counts` 与切点等长、非负、随切点单调不减；
* 切点 `c` 的计数 = 自该世代开始、**严格早于** `ts` 且延迟**严格小于** `c` ms 的请求数；
  隐含 0ms 切点计数为 0，隐含 +∞ 切点计数为 `total`；
* 计数与总数允许达到 2^64−1：仓库与结果库一律以十进制 TEXT 存储计数/总数，
  汇总用 Python 任意精度整数计算，不经过二进制浮点，也不受 SQLite 有符号 64 位整数限制；
* 字段必须恰好为上述 8 个，重复键、空行、浮点数、布尔值、非单调计数、`total` 小于最大桶计数等均为坏行。

### 值班表 JSONL（汇总时由管理员指定）

```json
{"region":"cn-1","collector":"a","generation":"g1","start":1700000000,"end":1700003600}
```

* 半开时段 `[start, end)`；同一 `(region, collector)` 的时段不得重叠（首尾相接允许），空档表示该采集器本来不值班；
* 入班、离班、同一时刻换班只来自此表，绝不从有没有数据反推。

### 班次请求 JSONL

```json
{"name":"morning","region":"cn-1","start":1700000000,"end":1700003600,"cuts_ms":[10,50]}
```

`name` 唯一；`cuts_ms` 为要查询的正整数毫秒切点（可为空数组，只查总数）。

## 命令

```sh
# 装载一批（批号幂等：同批号同文件重送返回原版本；同批号不同文件报错）
python3 -m histoware load --db wh.db --batch 2026-11-20T00 --file checkpoints.jsonl

# 查看批次与版本
python3 -m histoware batches --db wh.db

# 生成结果库（--version 省略时取当前版本）
python3 -m histoware summary --db wh.db --version 3 \
    --roster roster.jsonl --request shifts.jsonl --out result.db
```

可运行示例：`sh examples/run_example.sh`（手算数据：交集 A 起点总数 3、10ms 以下 2，
终点总数 7、只有 20ms 切点计数 4 → 新增 4 个请求、10ms 以下 ∈ [0,2]；
交集 B 恰有 1 个 10ms 以下请求 → 班次 10ms 以下 ∈ [1,3]，总数 5）。

## 班次回归归因（attribute）

### 配对清单 JSONL（每行一个配对）

```json
{"id":"week-over-week-10ms","baseline_shift":"base-week","candidate_shift":"cand-week","cut_ms":10}
```

* 字段恰好为 `id`、`baseline_shift`、`candidate_shift`、`cut_ms`；`id` 在清单内唯一，空行/重复 id/坏 JSON 整次运行失败；
* 两侧必须**实际包含同名班次、同一切点、同一区域**：按名称与切点显式配对，
  名称无关的猜测、按行顺序或相似名称配对一律禁止；
* 一个配对只比较一个切点；同一对班次要比较多个切点就写多行（不同 `id`）。

### 计算口径（全部整数运算，计数为十进制 TEXT）

对每一对班次，先按结果库 `intersection` / `intersection_cut` 明细在**区域 + 采集器**上对齐：

* 某采集器只有在两侧的**每个应覆盖交集都可用**（`ok`）且该切点都有上下界时才进入“可比较范围”；
* 采集器超阈值请求数 = 该采集器请求总数 − 该切点“**严格小于切点**”请求数。
  下界用 `总数 − below_hi`、上界用 `总数 − below_lo`，上下界保持结果库中的原有含义，
  绝不取中点、也不假设两侧误差相互抵消；
* 采集器贡献区间 = 候选区间 − 基线区间：`[cand.lo − base.hi, cand.hi − base.lo]`；
* 判定：变化下界 **> 0** 为 `confirmed`（已证实贡献）；上界 > 0 但下界不 > 0 为
  `possible`（可能贡献）；上界不 > 0 为 `unproven`（未证实）；
* 整体超阈值**比例的百分点变化**以精确分数（分子/分母各一列，分母为正）存储，
  不经过二进制浮点；分母为零时百分点列留 NULL 并给出 `zero_denominator` 原因；
* 可比较范围内各采集器区间之和**严格等于**该范围的整体变化区间（加法闭合）。
  当范围外还有采集器或不可用交集时，范围外部分以显式 `unallocated_lo/hi` 报告，
  绝不摊派给任何采集器；完全可比较时未分配部分恰为 `[0,0]`。

### 状态与保护

配对状态为 `comparable` / `partial` / `not_comparable`。出现零分母、任一侧覆盖不全
（`partial`/`no_duty`）、采集器集合不一致、缺切点、班次缺失或区域冲突时，绝不发布貌似确定的
整体归因：保留可定位的输入班次与全部交集证据（含两端检查点世代/修订/批号/行号），
在 `pair_issue` 中写明机器可读原因，并标注实际可比较范围（`comparable_collectors`）。

### 命令

```sh
python3 -m histoware attribute \
    --baseline examples/attr_base_result.db \
    --candidate examples/attr_cand_result.db \
    --pairs examples/attr_pairs.jsonl \
    --out examples/attr_compare.db
```

可运行示例：`sh examples/run_attr_example.sh`（手算：基线总 25、超阈值 [12,17]；
候选总 30、超阈值 [17,19]；采集器 a 精确 +3（confirmed）、b ∈ [-1,4]（possible）、
c ∈ [-2,0]（unproven）；整体变化 [0,7]，未分配 [0,0]；另含一个缺切点的 not_comparable 配对）。

### 对比库结构

* `meta`：schema 版本、三个输入文件 SHA-256、运行统计 `stats_json`；
* `input_file`：基线/候选/清单三个输入的路径、摘要、字节数、来源结果库 meta 摘要；
* `pair_request`：逐行配对请求（含原始 JSON 文本与行号）；
* `pair`：每对的状态、两侧班次/区域/状态、整体与**可比较范围**内的总数与超阈值上下界、
  变化区间、未分配区间、整体与范围内百分点分数边界、采集器计数；
* `pair_issue`：每对的机器可读判定原因（如 `baseline_cut_missing`、`collector_only_candidate`、
  `collector_not_comparable`、`zero_denominator`、`empty_comparable_scope` 等）；
* `pair_collector`：逐采集器是否在范围内、两侧 due/ok 交集数、两侧超阈值区间、变化区间与贡献判定，
  支持按配对班次和采集器查询；
* `pair_intersection`：两侧**每个来源交集**一行，带源交集 id、状态、冲突原因与完整检查点血缘，
  以及该切点在源库中的上下界，任何数字都可回溯到来源结果库。

### 一致性与原子性

* 两个输入结果库都以 SQLite **只读模式**打开，归因不会改动任何输入；
* 对比库先写临时文件、完整提交后原子改名覆盖目标，输入无效、配对冲突或写出失败都不会用部分结果覆盖已有库；
* 相同请求重跑逻辑结果一致（仅 `created_utc` 等运行时字段不同）；
* 交换基线与候选：所有变化区间符号反转、贡献判定相应调整，而可比较性状态不变。

## 版本退役（retire）

延迟仓接入生产后，运营只允许日常版本保留到最近一次核准的水位，正在复盘的几个老版本则必须能继续
重出原来的报表。`retire` 把“哪些入仓版本还可回放”与“这些版本仍会选中的检查点载荷”分开管理：
只看界面上的屏蔽减不掉数据，直接按入仓版本删行又可能删掉仍在用的端点。本实现给出**可预演、
可执行**的退役：先看见会失去哪些回放资格、实际会腾退多少载荷，再批准变更。

### 回放承诺

* **策略**是一个**不能倒退的入仓版本水位** `watermark` 加一组 `工单名 → 精确入仓版本` 的例外。
  版本 `V` 可回放当且仅当 `watermark <= V <= 当前版本`，或某个例外指向 `V`。
* 水位到当前版本之间（含两端）**全部可回放**；水位以下只保留例外所指版本。
* 多个工单可以保护**同一个版本**；去掉一个工单不会解除另一个工单的保护。
* 例外只能指向**变更前仍可回放**的版本；**已退役的版本不能重新挂回**。空工单名、同名重复、
  越界水位、未来版本都会被拒绝。
* **旧仓经显式初始化进入管理**（`retire init`）：初始水位 0、无例外，**不删除任何数据**。
  再次初始化是幂等的：不重置状态、不更换仓库标识。**未初始化的仓仍按旧方式使用**，完全没有
  退役过滤；用新程序访问旧仓不要求旧版可执行文件识别退役状态。

### 腾退什么

对一个端点 `(region, collector, generation, ts)`，把它的修订按**修订号升序**排列，每个修订带一个
入仓版本。入仓版本 `V` 看到的**可见修订**是“入仓版本 `<= V` 的修订中修订号最大者”。修订 `i`
被某个 `V` 选中，当且仅当 `v_i <= V < m_i`，其中 `m_i` 是所有**更高修订**中最小的入仓版本。
修订保留当且仅当可回放集合与 `[v_i, m_i-1]` 相交，即 `v_i <= max{可回放 R : R < m_i}`。

因此判定依据是**原来的最大可见修订语义**，而不是“载荷行自己的入仓版本是否还可回放”，
也不按检查点时钟裁切。迟到的低修订、以及同批进入、从未成为可见最大修订的记录，都按同一规则判断。
保留的端点、原有批号与行号**不被改写**；腾退**不分配新的入仓版本、不清批次账本、不更换仓库文件**。
腾退后的空闲页回到 SQLite 的 freelist，可被后续写入复用；**不要求文件立即缩小，也不承诺介质安全擦除**。
**已生成的汇总和对比库不改、不重写。**

### 命令

```sh
# 显式把旧仓纳入管理（幂等；水位 0、无例外、不删数据）
python3 -m histoware retire init --db wh.db

# 查看当前水位、例外、策略代次与回放/退役区间
python3 -m histoware retire status --db wh.db

# 预演：把完整目标策略写进文件，结果保存为可再提交的计划（不修改仓库）
cat > target.json <<'EOF'
{"watermark": 4, "exceptions": [{"work_order": "wo-1", "version": 1}]}
EOF
python3 -m histoware retire plan --db wh.db --target target.json --out plan.json

# 批准：重新核对计划与修订集合后原子执行，返回收据
python3 -m histoware retire approve --db wh.db --plan plan.json

# 事后按计划标识查询收据（进程退出后仍可查）
python3 -m histoware retire receipt --db wh.db --plan-id <plan_id>
```

### 计划读法

`retire plan` 输出的计划（同时也是 `--out` 保存的内容）包含：

| 字段 | 含义 |
| --- | --- |
| `plan_id` | 计划的确定性摘要，绑定仓库标识、预演时的当前版本、策略代次与规范化目标策略 |
| `warehouse_id` | 仓库标识；计划不能跨仓执行 |
| `base_current_version` | 预演快照的当前入仓版本；之后有新入仓即失效 |
| `base_policy_generation` | 预演时的策略代次；之后有策略变更即失效 |
| `target` | 规范化后的完整目标策略（水位 + 全部例外） |
| `newly_retired_versions` | 本次新增失去回放资格的版本区间（如 `[[2, 3]]`） |
| `replay_intervals_after` | 执行后的可回放区间 |
| `retained_payload_rows` / `retained_payload_bytes` | 保留的载荷行数与规范化字节数 |
| `evicted_payload_rows` / `evicted_payload_bytes` | **拟移除**的载荷行数与规范化字节数 |
| `eviction_digest` | 稳定标识准确移除集合的摘要（对每个被删修订的身份 + 规范化载荷摘要做与顺序无关的折叠） |
| `stats` | `classification_passes`（恒为 1）、`revisions_examined`、`endpoints_examined` |

“规范化载荷字节数”按约定的[规范化载荷编码](#规范化载荷编码)计量，**不是文件大小之差**。
对同一仓状态与同一目标内容，`plan_id` 与上述业务结果都应一致（演练会核对）。

### 批准语义

* 批准时**重新读取计划、重新按当前状态推导腾退集合**，不信任计划自己写的计数：串仓、
  计划被改动、或预演之后另有入仓 / 策略变更，都会被拒绝并提示重新预演。
* **成功的同一计划再次提交**（即使随后又有新入仓或后续策略）返回**原收据**，不再执行；
  修改原计划再借用其标识会被拒绝（计划标识覆盖全部业务字段）。
* 水位、工单、载荷腾退、保留的接收凭据和收据是**一次持久状态转换**：策略更新、行删除、内容凭据、
  退役收据在同一事务内提交。执行过程中被中断或写入出错时，外部读不到只改了一半的策略，
  也不会登记虚假的成功收据（演练用 `os._exit` 在提交前杀进程验证）。
* 预演、批准与入仓**按持久提交顺序**定序：批准在写事务内重新核对当前版本与策略代次，
  因此一份计划不会在拿到批准后悄悄吞掉计划外的新数据。
* 收据字段：`receipt_id`、`plan_id`、`warehouse_id`、`base_version`、`evicted_rows`、
  `evicted_payload_bytes`、`policy_generation`、`created_utc`，以及 `detail`（含新增退役区间、
  保留行数/字节数、`freelist_pages_before/after`、载荷编码与“文件不缩小/不擦除”的说明）。

### 已退役版本与日常业务

* **汇总**：新开始的 `summary` 若明确选中已退役版本，会以**可区分的退役错误**失败
  （`error: retired version: ...`，退出码 2），不生成貌似缺报的汇总，也不触碰已有目标文件。
  可回放性在读取端点的**同一快照**内判定；已经建立快照的汇总可以按旧视图做完。
* **入仓**：历史批次原文件重送仍返回原入仓版本，即使其中修订已退役；新批次遇到已腾退的
  **同身份同修订**，等价载荷视作重传、**不复活旧行**，异内容仍整批拒收并能定位**首次来源**
  （批号 + 行号 + 入仓版本）。
* 为此只为被腾退的修订保留**最小接收凭据**（键、首次版本与出处、规范化内容摘要），
  不把拟腾退的桶、计数和总数搬到影子表。
* 新检查点照常接收，之后可以再次预演。

### 规范化载荷编码

一个检查点载荷的规范化编码是键序固定的紧凑 UTF-8 JSON：

```
{"collector":...,"counts":[...],"cuts_ms":[...],"generation":...,
 "region":...,"revision":...,"total":...,"ts":...}
```

字符串按 ASCII 转义，整数一律十进制，`cuts`/`counts` 使用与仓库中相同的紧凑数组文本。
计划与收据里的“字节数”“内容摘要”都以此为准。

### 安全地从旧仓开始

1. 备份仓库文件（例如 `cp wh.db wh.db.bak`，若使用 WAL 请一并备份 `-wal`/`-shm`）。
2. `retire init --db wh.db` 把仓库纳入管理（水位 0、无例外，不删数据；可重复执行）。
3. `retire plan` 预演：核对 `newly_retired_versions`、`evicted_payload_rows/bytes`、`eviction_digest`。
4. 确认无误后 `retire approve`，并用 `retire receipt` 留档。
5. 日常 `load` / `summary` 行为不变；只有明确选中已退役版本才会报退役错误。

### 可复跑演练

```sh
python3 examples/retire_drill.py
```

脚本在临时目录生成数据、逐项打印 PASS/FAIL，覆盖：水位 4 + 单工单保护版本 1（只留下修订
20、35、50，版本 3 即便与版本 4 选中同一行也拒绝新建汇总）；两个工单指向版本 1 后分别解除；
40 个随机稀疏/连续策略场景与独立逐版本枚举对照；清退前后保留版本汇总的检查点结果与来源不变；
旧批重送、已腾退修订的等价重传与冲突、批准与新批次交错导致计划失效、已开读快照跨过批准，
以及进程在事务未提交时被终止后重新打开仓库的结果。

## 检查点镜像（mirror）

配送区域的值班机有时连续几小时连不上中心延迟仓，但现场排障仍要查到各探针**最近同步到的累积检查点**，
包括该行最初由哪批、哪一行送来。给现场拷一份班次结果库无法从已确认的位置继续接收；每次复制整个管理仓
又会带上其他区域、历史修订和管理账本。`mirror` 用**文件交接**解决这个问题：中心把端点的**当前选中行**
按订阅导出成自包含的包文件，现场离线接收进一个独立的 SQLite 镜像库并直接查询——首次安装、推进与重建
都不需要现场能连到中心。镜像的是端点选中行，不是班次结果，也不需要值班表；镜像库只是查询副本，
**不能**冒充中心仓调用 `load` / `retire`，源仓仍是同一标识下唯一的权威写入方（不做双主合并）。

### 订阅

镜像固定订阅**全部区域**（`--regions all`，后续新出现的区域自动包含）或一个**非空的明确区域集合**
（`--regions cn-1,cn-2`，地区名单按集合比较，与顺序和写法无关）。订阅是包身份的一部分，也固定在
镜像库里：订阅不匹配的包一律拒收。

### 包格式（`histoware-mirror-package`，格式版本 1）

包是 UTF-8 JSONL，每行一个键序固定的紧凑 JSON 对象，可逐条读取：

* 第 1 行 `header`：格式名、格式版本、包类型（`base`/`delta`）、源仓标识、订阅、快照版本（base）或
  闭区间 `[base_version, end_version]`（delta）；
* `row`（仅 base）：B 时订阅范围内每个端点被选中的完整行——未经汇总的切点、累积计数、总数、修订和
  首次来源（`first_version`/`first_batch`/`first_line`）——按端点键严格升序；
* `unit` + `change`（仅 delta）：(B, E] 每个提交版本一个 `unit`，**按序、不缺号**（没有订阅内变化的
  版本也保留空单元），`unit` 记录原入仓批号与本单元变化数，随后恰好是那么多条 `change`，按端点键
  严格升序；`change` 区分**首次出现**（`old_revision` 为 null）与**替换**（`old_revision` 带上预计被
  替换的修订），新值含完整载荷与首次来源，且首次来源必须指向本单元的版本与批号；
* 最后一行 `trailer`：明确的结束边界——记录数、分类合计，以及对前面全部字节（头部 + 数据）的
  SHA-256 摘要。

计数与总数全程是精确十进制整数（不转浮点、不截断大整数）。包内没有机器路径或生成时间：
**同一源视图、同一区间、同一订阅重导出得到逐字节相同的包**。

### 什么才算一条变化

端点在某版本被选中的修订 = 入仓版本不超过该版本的最大修订。某个提交单元有且仅有一条更新，当且仅当
该端点在提交前后选中的修订不同；一个单元里多个端点变化时每个变化键各有一条。同批先到 8 后到 10 只发布
最终选中的 10；后一批迟到的 9 不是变化；但第 13 批选中 11、第 14 批选中 12 时两个提交的变化都保留，
不会只写范围终点的 12。

### 导出资格与一致性

* 导出只读**已管理**仓库（标识来自 `retire init`；未初始化给出明确提示），不隐式改变保留策略，
  也不为支持追更在中心另存已腾退的载荷。
* 起始包要求版本 B 可回放（0 是空仓版本，只在可回放时才能作为起点）；追更包要求**闭区间 [B,E] 全部
  可回放**——即使 B 是受保护的孤立版本、E 也有效，中间有退役版本就报告**第一个缺口**，绝不通过查找
  较新的行或对比两端最终状态假装连续。
* 一次导出的资格检查、批次读取与选中行读取都在**同一个仓库读视图**（WAL 快照）内：导出中途有新提交或
  腾退，只完整交付原视图，不把新策略和旧行拼成一个包。
* 包先写临时文件、完成后原子改名；失败不替换原目标文件。
* 追更导出按 `(version)` 索引做区间扫描，再对每个涉及端点做一次主键探测：已建好索引后，工作量随
  **涉及批次和变动**增长，不为每个版本枚举整仓；起始导出允许遍历必要数据。包与镜像都流式读写，
  不在内存保留整段包或整个镜像。

### 接收语义

* 读者拒绝：截断、数据损坏、非法内容、同一提交内重复的键、遗漏或乱序的提交单元、计数或摘要不符、
  尾部之后还有内容。
* 追更包只允许接在现场**当前游标**之后；串仓、串订阅、“预期不存在／预期旧修订”与现场不一致，都不能
  悄悄接收；范围与已接受进度重叠或留缝的不同包不做部分拼接。
* 镜像行、游标和本包收据在**一个事务**里落定：多版本追更包不会只应用一半就对查询者可见；被中止的
  接收或重建不留下部分新行、跳过的游标或成功记录。两个接收进程争用同一现场库时，以实际提交状态检查
  起点和旧修订。
* **收据**离线可查：源、范围、包摘要、代次和接受的变化数。原样重送本代次已接收的包返回已有收据，
  即使后来又推进了版本；不同内容不能借用已有包的身份（身份即内容摘要）。
* **断档恢复**：中心发现断档时现场原库仍按原游标查询；恢复由操作者明确用同源、同订阅且比现场游标
  更新的起始包**重建**（`receive --rebuild`）。重建以新代次**替换**端点全集，不把两份快照合并；
  过去的收据仍可供审计，但不能作为新代次接收旧追更包的依据。

### 命令

```sh
# 中心：导出 B 时刻的起始包（建立新的镜像代次）
python3 -m histoware mirror export-base --db wh.db --regions all --version 12 --out base12.pkg

# 中心：导出从已持有的 B 推进到 E 的追更包（依次携带 B+1..E 每个提交单元）
python3 -m histoware mirror export-delta --db wh.db --regions cn-1,cn-2 --from 12 --to 15 --out d12-15.pkg

# 现场（离线）：接收、重建、查状态
python3 -m histoware mirror receive --db mirror.db --package base12.pkg
python3 -m histoware mirror receive --db mirror.db --package d12-15.pkg
python3 -m histoware mirror receive --db mirror.db --package base20.pkg --rebuild
python3 -m histoware mirror status --db mirror.db
```

可运行示例：`sh examples/run_mirror_example.sh`；端到端演练（41 项检查）：
`python3 examples/mirror_drill.py`。

### 镜像库结构（稳定的 SQLite 查询接口）

* `meta`：`mirror_schema_version`、`generation`（代次）、`cursor`（当前游标）、`warehouse_id`、
  `subscription`（规范化订阅 JSON）；
* `mirror_row`：每个端点当前选中的一行——`(region, collector, generation, ts)` 主键，
  `revision`、`cuts`/`counts`（紧凑 JSON 数组文本）、`total`（十进制 TEXT）、
  以及首次来源 `first_version` / `first_batch` / `first_line`；
* `receipt`：每个已接收包一行——代次、类型、源仓标识、订阅、范围（`base_version`/`end_version`）、
  包摘要 `package_sha256`、记录数、接受的变化数、接收时间。

现场不需要连接中心即可用任意 SQLite 客户端读出当前游标、端点和出处，例如：

```sql
SELECT collector, generation, ts, revision, total, first_batch, first_line
FROM mirror_row WHERE region = 'cn-1';
```

## 语义要点

* **版本与幂等**：每整批成功分配一个递增版本；同一检查点同修订、语义相同的重传不产生第二个修订、
  不改变最初批号/行号；内容不同则拒绝整批。更高修订可改变桶布局；迟到的低修订被保留但不会取代高修订。
  坏行、批内/与既存资料冲突、读入中断都不会推进可见版本，历史版本仍可重算。
  已退役版本上的重传与冲突按[版本退役](#版本退役retire)的接收凭据处理。
* **交集**：班次与值班时段求交，正长度交集取**精确起止整秒**的检查点（同一值班世代、
  指定版本可见的最大修订）。缺端点不补零、不用邻近时刻代替；中间漏报不影响两端齐全的交集；
  跨班次的大交集计数从不按时长摊回小班次。换班时旧世代终点与新世代起点是两条不同记录。
* **冲突**：总数倒退、共同切点（含隐含端点）差值不单调、或某查询切点区间裁剪后为空，
  该交集整体记为 `conflict` 不可用，并记录发生冲突时所用的修订与切点，不回退旧修订。
* **区间估计**：两端都有该切点则精确作差；否则各端用相邻已知切点（含隐含 0/+∞）夹住累积计数，
  以「终点下界−起点上界、终点上界−起点下界」得区间，再与 `[0, 交集请求总数]` 相交。
  禁止插值、细分原桶或把有限上界写成精确值。
* **班次状态**：`complete`（全部应覆盖交集可用，给出总数与区间，上下界相等即 `exact=1`）、
  `partial`（有缺报/冲突：只发布带标记的已覆盖小计 `covered_*`，整体指标留空 NULL）、
  `no_duty`（零值班交集的专门状态，与完整零流量 `complete` 且总数 0 严格区分）。

## 结果库结构

* `meta`：入仓版本、值班表/请求内容摘要（SHA-256）、运行统计 `stats_json` 等；
* `shift` / `shift_cut`：按班次的总计与每切点上下界（计数为十进制 TEXT）；
* `intersection`：每个应覆盖交集的状态、两端检查点的世代/修订/批号/行号、两端总数与差值、冲突原因与切点；
  缺端点时保留另一端并注明缺哪端；
* `intersection_cut`：每个查询切点用于判断上下界的**原始相邻切点与计数**
  （切点 0 = 隐含零切点，NULL 切点 = 隐含 +∞，其计数为该端总数）。

## 索引、内存边界与一致性

* 端点查找走检查点主键索引 `(region, collector, generation, ts, revision)` 的 O(log n) 探测，
  并为每个班次/全部班次**从不重扫**检查点历史；相邻班次共享的端点由有界 LRU 缓存（默认 65536 条）复用；
* 镜像追更导出另有一次性建立的支持索引 `ix_checkpoint_version(version)` 与 `ix_batch_version(version)`
  （随建库与任何写连接自动创建）：追更按版本区间扫描涉及批次，再对每个涉及端点做一次主键探测，
  工作量不随仓库总大小增长；
* 装载与值班表使用文件后备临时表（`PRAGMA temp_store=1`）分块写入，整个文件从不一次装入内存；
  班次逐个处理、结果行定长分块写出，单班次工作内存只与该班次覆盖的值班时段数有关；
* 汇总期间全部仓库读取处于同一 WAL 快照事务并叠加 `version <= V` 过滤：
  即使此时有新批次提交，结果中也读不到比所选版本更新的端点；
* 结果库先写入临时文件、提交成功后原子改名覆盖目标，失败不会把已有结果换成部分完成的数据库；
  历史重算保证表内逻辑结果一致（不要求 SQLite 文件逐字节相同）；
* 每次汇总在 stdout 与结果库 `meta.stats_json` 中报告实际的端点查找次数、缓存复用次数与各表写出行数。
